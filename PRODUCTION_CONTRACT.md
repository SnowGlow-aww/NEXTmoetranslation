# Locale And Lyrics Production Contract

This document records the additive contract implemented on top of legacy baseline `bbc3340`. The baseline behavior and fixtures in `LEGACY_BASELINE.md` remain authoritative for requests without an explicit locale and for all existing public files.

## Database Migrations

Migrations are applied in version order inside individual SQLite transactions. Each applied row records its version, name, SHA-256 checksum, and timestamp in `schema_migrations`; startup rejects changed or newer migration histories.

1. `multilingual_content_and_lyrics` adds locale side tables, stable event segments, catalog tables, lyrics drafts, line segments, and publication snapshots. It backfills only source text that the legacy schema actually retained.
2. `lyrics_source_provenance_and_stanzas` adds immutable source revision identity and stanza boundaries.
3. `lyrics_catalog_source_identity` adds catalog producer metadata used to reject ambiguous external source matches.
4. `rolling_event_side_tables_no_legacy_cascade` removes cascades from legacy story parents so a previous binary's replace-import cannot erase multilingual content. Current imports explicitly reconcile stable segment rows.
5. `stable_event_title_segment_identity` upgrades migrated title IDs to the same positional `:title:-1` identity used by current imports without losing existing localizations.
6. `mark_legacy_event_talk_identity` retains migrated talk positions as opaque `:legacy` IDs because filtered legacy output cannot truthfully identify `body` versus `speaker`; localization rows and source hashes move with those IDs. A current-format reimport reserves matching stable IDs first, then carries a localization to a different ID only when its source occurrence was unique before reimport and identifies exactly one unclaimed episode/kind/hash destination afterward.
7. `public_lyrics_attribution_and_token_generation` adds operator-authored public lyrics attribution and per-user token generations. Existing lyrics publication snapshots are cleared because private notes cannot be substituted for public attribution; drafts remain intact and require attribution before an administrator republishes them.
8. `event_story_scenario_snapshots` adds a no-parent-FK side table keyed by event/episode for deterministic compact JP Unity scenario JSON and SHA-256. The lack of a legacy parent FK is intentional: an older writer can continue replacing event parents without cascading private scenario snapshots, while current reads validate parent/scenario identity and fail closed.
9. `retain_rolling_event_segment_recovery_rows` removes the event/episode/kind/position uniqueness constraint from stable segment recovery rows. This preserves displaced localization recovery candidates during rolling legacy/current event imports; the primary segment ID and localization foreign key remain authoritative, and current reconciliation still validates source identity before carrying content forward.
10. `durable_lyrics_discovery_jobs` adds the fenced at-least-once queue used by automatic lyrics-source discovery. Job identity, attempts, lease ownership/expiry, retry scheduling, terminal state, and optimistic version are persisted; this migration remains unchanged after application.
11. `lyrics_discovery_shadow_results` append-only extends the queue with catalog fingerprint and policy generation, then adds the private Shadow result table. Composite foreign-key identity prevents a result from being attached to a different catalog or policy generation; outcome/count/JSON constraints fail closed before persistence.

Before the first pending migration in one startup, file-backed databases receive a verified `*.pre-migration-vN.bak` SQLite backup, where `N` is that first pending version. A multi-version jump therefore produces one recovery point for the pre-upgrade database, not one backup per intermediate migration. Startup also requires the recorded migration history to be a contiguous prefix with matching names/checksums and runs a full `PRAGMA integrity_check` after schema/migrations before returning the database to the server. Migration tests cover idempotent reopen, checksum/gap refusal, injected rollback, backup recovery, legacy writer compatibility, private file modes, old event replacement, the unchanged v10 checksum, v11 upgrade/rollback/constraint behavior, and append-only v12 integer-type guards for the durable discovery queue and shadow results.

The SekaiText category snapshot/batch and projection-status contracts require no additional schema: category revisions are derived from point-in-time content, and event optimistic concurrency uses the existing localization revision columns.

Migration v9 requires a single-instance `Recreate` rollout. Before starting the v9 binary, stop the old instance and create a verified full SQLite off-host backup with SQLite backup/VACUUM semantics. Do not run old and new writers concurrently and do not roll back an old binary onto a v9 database. A `*.pre-migration-v9.bak` exists only when v9 is the first pending migration for that startup; when upgrading across v8 and v9 together, restore the verified backup named for the first pending version (for example `*.pre-migration-v8.bak`) or the off-host snapshot as described in `ROLLBACK_RUNBOOK.md`.

## Console APIs

The optional `locale` on `GET /api/categories`, `GET /api/entries`, `PUT /api/entry`, `GET /api/event-stories`, `GET /api/event-story`, and `PUT /api/event-story/update` accepts only `ja-JP`, `zh-CN`, and `en-US`. Omitted locale delegates to the exact legacy Chinese code path; explicit `zh-CN` event detail reads use the localized segment projection and its mutations and audit rows commit atomically without changing omitted-locale behavior; `ja-JP` is source-only and rejects writes; `en-US` is stored independently and is never changed by CN sync or AI translation. Localized event rows expose IDs and source hashes, and every explicit-locale write, including `zh-CN`, must echo and validate the full episode/type/key/ID/hash identity or receive a contract error or conflict.

SekaiText-Moe can use three additive authenticated routes without changing the legacy per-field routes:

- `GET /api/category/snapshot?category={category}&locale={locale}` requires an explicit supported locale and returns `{category, locale, revision, fields}` for every source-backed identity in every category field from one SQLite transaction. `revision` is an opaque URL-safe digest over source identities, IDs, and locale values; clients must not construct or interpret it.
- `PUT /api/category/batch` accepts `{category, locale, baseRevision, updates, clientId?}`. It rejects a stale complete-category revision or any unknown/duplicate entry identity before writing, then applies all changed entries and their content-minimized audit rows in one transaction. One post-commit change notification schedules public generation, and one existing `entry.updated` or `entry.locale.updated` SSE frame is emitted per changed entry after commit. Success returns the fresh full `{category, locale, revision, fields}` snapshot plus `updated`; stale revisions return `revision_conflict` with the current snapshot.
- `GET /api/projection/status` returns the last published `generation`, whether a rebuild is `pending`, `lastSuccessAt`, and a sanitized `lastError`. Initial generation runs asynchronously after the listener is acquired, so liveness and signal handling are available while readiness remains false. `/readyz` remains false for every pending generation, even before an error is known, preventing restore or write traffic from being admitted while authenticated SQLite state and public files are temporarily different. Every failed requested publication, including a failure after an earlier success, retries with bounded exponential backoff until the latest requested generation publishes or shutdown cancels the worker. Database persistence is complete when the batch returns; public `/files` and `/translation` bytes for that save are rebuilt only after the post-save status reaches a later non-pending generation with an empty `lastError`.

### Single-Instance Editor Gate

The server process owns one writer-preferred editor gate. `GET /api/editor-gate/status` requires JWT authentication, is `Cache-Control: no-store`, and returns exactly version 1 `{version, instanceId, revision, generation, completedGeneration, running, lastRun}`. `instanceId` is a random 32-byte base64url value generated for each process start. All counters remain within JavaScript's safe integer range. Initially all counters are zero, `running` is false, and `lastRun` is an empty string. Producer start increments `generation` and `revision` and publishes `running=true` before waiting for existing editors; completion, including failed jobs, sets `completedGeneration=generation`, increments `revision`, records an RFC3339 completion time, clears `running`, and releases waiters. Therefore `completedGeneration <= generation`, and while running the generation is exactly one ahead of the completed generation.

Producer-aware clients use these strict aliases:

- `PUT /api/editor/v1/entry`
- `PUT /api/editor/v1/category/batch`
- `PUT /api/editor/v1/event-story/update`
- `POST /api/editor/v1/event-story/promote-human`
- `PUT /api/editor/v1/lyrics/save`
- `POST /api/editor/v1/lyrics/publish`
- `POST /api/editor/v1/lyrics/unpublish`
- `POST /api/editor/v1/backup/push`

Every strict mutation must send exactly one `X-Moe-Loaded-Producer-State: <instanceId>:<completedGeneration>` header from the status loaded with the edited document. A missing header returns `428`; a duplicate or malformed/base64/non-canonical/out-of-safe-range value returns `400`; an active producer, stale completed generation, or process-restart instance mismatch returns `409` with the exact current producer status object. Validation and shared editor acquisition are atomic, and the atomically accepted producer status is carried in request context rather than reacquired inside handlers. Existing canonical mutation paths require no new header and remain compatible, but immediately return `409` while a producer is running rather than waiting to apply a stale payload afterward. A lyrics save carrying `sourceImportToken` is the exception: the canonical `/api/lyrics/save` route fails closed with `428`, and verified imports are accepted only through `/api/editor/v1/lyrics/save`. Source preview is revision-zero/first-save-only, compares exact stopped producer status before and after the external fetch, and rechecks that no lyrics document was created during that fetch before issuing any token. Its grant binds user, music, exact preview, expiry, and the complete atomically accepted producer status; claim marks it in flight. Correctable draft validation, database/transaction/internal failure, and 5xx outcomes release the exact claim for retry. Success and deterministic invalidation—expiry, user/music mismatch, producer drift, source/preview drift, nonzero revision, or an already-existing first-save target—commit/consume the exact claim. After claim, `SaveImportedLyricsMutation` retains the fixed per-music stripe across eligibility checks and the complete SQLite transaction; terminal classification occurs only after it returns, and the Store has no grant callback or burn-on-attempt hook. An impossible exact-claim commit failure after a durable save is logged as an internal invariant, the token is invalidated fail-closed, and the API preserves the truthful successful save response rather than reporting a false retryable failure. Concurrent use of one token permits only one claimant. Translation sync, all AI/retry/reorder translation operations, and backup restore are producers. Duplicate producers fail immediately instead of waiting. The existing `/api/translate/status` response shape remains unchanged for native proxy compatibility.

Explicit-locale event detail segments also expose their translation `revision`. `PUT /api/event-story/update` conditionally rejects a competing localized translation with `revision_conflict` when the client echoes `revision`; omission retains the prior authenticated client behavior. Event revisions are removed before public v2 serialization, so no existing public event bytes change.

`GET /api/event-story/episode-snapshot?eventId={id}&episodeNo={episode}&locale={locale}` is authenticated and requires an explicit supported locale. A single SQLite read transaction returns event/episode/locale identity, an opaque revision covering scenario SHA plus segment identity/source hash/text/source/revision, the localized episode segments, and `scenario` with `{scenarioId,fileName,sha256,parserVersion,rawJson,sourceTalks}`. `rawJson` is deterministic compact JSON containing the complete JP `ScenarioId`, `Snippets`, `TalkData`, `SpecialEffectData`, and `AppearCharacters`; SHA, parent identity, scenario identity, and canonical form are revalidated before any raw data is returned. Parser version 1 follows the public SekaiText Next JSON loader order for TalkData, close-window blanks, effect types 8/18/23 and trailing-blank removal, and exposes `talkDataIndex` on TalkData rows so body/speaker segment positions map to `i*2`/`i*2+1`.

Lyrics and catalog routes are authenticated:

- `GET /api/catalog/music`
- `GET /api/catalog/characters`
- `GET /api/lyrics` and `GET /api/lyrics/detail`
- `PUT /api/lyrics/save` for editors and admins
- `POST /api/lyrics/publish` and `POST /api/lyrics/unpublish` for admins
- `GET /api/lyrics/source/search` and `POST /api/lyrics/source/preview` for admins

Lyrics use numeric `musicId`, stable ordered line IDs, Japanese/Chinese/English text, ordered text segments, required unique catalog performer IDs for publication, optimistic revisions, immutable Japanese source hashes and source provenance, draft/publication separation, and idempotent save/publish/unpublish behavior. An ordinary first save may omit `sourceUrl` or store a valid non-managed external reference. A URL on the exact managed Vocaloid Wiki origin, whether or not it includes `oldid`, is rejected on an ordinary first save; complete page/revision/SHA1/fetch provenance for that origin is accepted only through the verified preview/import methods. Other Fandom or Wiki origins are not classified as managed merely by platform or naming similarity. Existing legacy drafts that contain only a managed-Wiki URL remain editable only while the source URL, provenance fields, ordered line IDs/order values, and Japanese source text remain unchanged. Every provenance-bearing save and restore requires an exact lowercase 40-hex source SHA1; short, uppercase, non-hex, or opaque values fail closed. Source lookup pins page and revision identity, rejects cross-origin redirects and explicit no-reprint markers/categories, and records source access in the audit log; contract errors use sanitized codes including `revision_conflict` (409), `source_drift`, `segment_mismatch`, `invalid_performer`, and `incomplete_publication` (422).

Pinned page/revision/SHA1/fetch identity establishes consistency with the fetched revision; it does not establish copyright ownership, permission to reproduce or translate, license compatibility, or permission to publish. Public lyrics publication requires non-empty operator-authored `attribution`, which is the only public source-context metadata field. `attribution`, private `licenseNote`, and private `sourceNote` are operator metadata rather than verified grants or legal conclusions. Source notes, license notes, source URL, page/revision/SHA identity, fetch timestamps, editor identity, and draft status remain confined to authenticated APIs and backups. Canonical JSON Schemas and consumer fixtures for Moesekai are committed under `contracts/public-lyrics/v1/`; NEXT paths and field names remain authoritative and no duplicate compatibility editing endpoints are exposed.

Phase 1 automatic discovery is Shadow-only and disabled by default. `LYRICS_DISCOVERY_ENABLED=true` is seeded only when the setting is absent; after first seed, `lyrics_discovery.enabled` in the authenticated settings store is authoritative. When enabled, one worker scans the complete ordered music catalog, derives each job generation from the catalog fingerprint plus the fixed Shadow policy version, and queries the bounded Vocaloid Wiki source client. It persists only compact candidate summaries in `lyrics_discovery_shadow_results`; no fetched lyric text, raw response body, draft, publication, translation, projection notification, or public file is created or changed. Catalog drift is terminal for that generation. Result insertion and transition to `succeeded` share one SQLite transaction with owner/version fencing; retryable failures use the durable queue, while terminal failures dead-letter the lease. Scan, lease, idle, retry, and per-job timeout values are environment-configurable in milliseconds through `LYRICS_DISCOVERY_SCAN_MS`, `LYRICS_DISCOVERY_LEASE_MS`, `LYRICS_DISCOVERY_IDLE_MS`, `LYRICS_DISCOVERY_RETRY_MIN_MS`, `LYRICS_DISCOVERY_RETRY_MAX_MS`, and `LYRICS_DISCOVERY_JOB_TIMEOUT_MS`; invalid ranges fail startup, and the job timeout must be shorter than the lease. The worker starts only after successful TCP bind and shutdown orders `Drain`, `Cancel`, and `Wait` before SQLite closes. Phase 2 snapshot/review artifacts and Phase 3 draft promotion are not implemented by this contract.

JSON request bodies are capped at 8 MiB, reject unknown fields, trailing second values, and duplicate object keys at every nesting level, and the HTTP server bounds both header and whole-request read time. External lyrics-source requests use response caps, rate limiting, cache bounds, origin-locked redirects, and timeouts. HTTP responses carry a sanitized `X-Request-ID`; `/readyz` requires SQLite, at least one successfully published initial public projection with no known latest-generation failure, and a live or validated cached search index. Search masterdata must pass per-source identity, minimum-coverage, and nonreduction checks before replacing the last-known-good assets, and its local translation reads share one restore exclusion boundary. Authenticated `/api/search/status` and admin-protected `/healthz/details` expose the search ready/degraded state and sanitized failure code; health details also report lightweight request/client-error/server-error counters, while `/healthz` remains independent liveness with its existing body. Operational responses are `no-store`. On drain, all new HTTP work, including reads, static files, SSE, and CORS preflights, is rejected with observable, logged, CORS-enabled `503` responses; only exact `GET`/`HEAD` `/healthz` and `/readyz` probes remain admitted, with readiness returning not-ready. Active probes remain tracked until force-close shuts their admission gate, so their handlers join before the watchdog stops and SQLite closes without a WaitGroup Add/Wait race. One configurable total shutdown budget includes a short HTTP drain, cancellation, forced HTTP close, and all tracked worker/request joins before SQLite closes. Local loops, archive/copy work, network requests, and restore transactions honor cancellation where tractable. If a noncancelable filesystem or SQLite critical section still exceeds the total budget, a process watchdog logs a critical fail-closed message and exits without closing SQLite under live goroutines rather than hanging until the platform sends `SIGKILL`. Locale, lyrics, source, and restore mutations/accesses write content-minimized audit rows. Editor mutations accept only the closed translation source vocabulary `cn`, `human`, `pinned`, `llm`, and `unknown`; invalid category-batch, legacy entry, event, or applicable lyrics translation-source values return `400` before persistence.

- `/files/v2/{locale}/translation/{category}.json`
- `/files/v2/{locale}/translation/{category}.full.json`

Raw event scenario snapshots are authenticated/private data and are never added to legacy or v2 public JSON generation.

## Backup And Restore

Git and S3 backups retain the legacy category/event `translations` restore projection, physically archive canonical public lyrics as `translations/lyrics/index.json` and `translations/lyrics/music_<id>.json`, and add `translation-content/manifest.json`. The archived public lyrics bytes must exactly equal the corresponding `PublishedLyricsJSON` bytes from the same SQLite snapshot. `Generator.WriteAllContext` keeps its general legacy category/event output contract; `materializeBackupPayload` explicitly adds public lyrics assets only to the backup archive from the snapshot-backed generator. Both backup projections are materialized from one SQLite snapshot; manifest schema version 1 checksums and counts multilingual entries, stable event content, catalog/lyrics drafts, source provenance, and publication snapshots. Drafts, private provenance, and publication database state remain preserved by `translation-content/lyrics.json` so runtime `filesvc` can atomically regenerate the public set after restore. V2 locale projections and search indexes are not archived. Backup push is content backup only, not deployment, static publication, or CDN synchronization. Legacy and additive restore data commit in one transaction, failure rolls everything back, and backups without the additive directory explicitly clear multilingual/lyrics-only state while retaining the old public restore projection. User tables, password hashes, settings, token generations, audit records, and secrets are not exported. Consequently this content backup is not a full database backup. `BackupAll` fails, does not advance `LastBackup`, and does not consume scheduler success when both targets are disabled.

Schema-version-1 `translation-content/event-stories.json` additionally contains canonical scenarios. Its legacy `count` remains segments + localizations + locale metadata, while optional `scenarioCount` validates the new rows; SHA and parent/scenario identity are checked before the restore transaction replaces anything. Older additive or legacy backups without scenarios explicitly clear scenario snapshots.

Restore safety limits keep ordinary files at 64 MiB while allowing only `translation-content/event-stories.json` up to 512 MiB; expanded archives remain bounded at 1 GiB, compressed S3 responses at 256 MiB, and additive content at 1,000,000 aggregate typed records.

Production operations must additionally create full SQLite snapshots with SQLite's online backup API, `.backup`, or `VACUUM INTO`, verify `PRAGMA integrity_check`, encrypt the snapshot, and transfer it to independently controlled off-host storage. Copying only the main `.db` file while WAL writes are active is not a valid backup. Full snapshots require tested retention and restore procedures and must be taken before migration v9 and before rollback-sensitive releases.

## Authentication And Operations

JWTs carry a persisted per-user token generation and are accepted only while the user still exists and the current database role and generation match. Password changes and role changes advance the generation, deletion removes the validation row, and all three operations immediately reject previously issued tokens. Public setup and login attempts are bounded in memory by both the normalized account and the socket `RemoteAddr`; forwarding headers are intentionally ignored. First-admin creation performs the empty-user check and insert in one immediate SQLite transaction.

Editors may proofread individual entries, event lines, and lyrics drafts. CN sync, every AI trigger, event retry/reorder/promote, backup push/restore, user/settings/upstream administration, and lyrics publication are admin-only; read-only status and catalog endpoints remain available to authenticated editors.

Production rollback is defined in `ROLLBACK_RUNBOOK.md`, including immutable artifact/image selection, database migration compatibility, credential/key handling, and post-rollback verification.

Production mode is explicitly enabled with `MOESEKAI_PRODUCTION=true`, and the paired image persists that value in its runtime environment. It requires at least 32 bytes of `MOESEKAI_MASTER_KEY` secret material, at least one initialized admin, `WORKSPACE_WEB_DIR`, and the external artifact lock `WORKSPACE_MANIFEST_SHA256`; a fresh database must receive a valid `ADMIN_PASSWORD` or `TRANSLATOR_ACCOUNTS` bootstrap secret. `editor` and `admin` are the complete role vocabulary: user creation, login, token issue/verification, and startup reject any other persisted role. Development and tests retain setup defaults and may use a short or absent master key. If either workspace variable is configured, both are required and the complete immutable pairing verification runs before database ownership/open; production requires both producer `sourceDirty=false` and `sourceProduction=true`. Seed migration reconciles only nonconflicting flat/full unions, verifies the complete union through SQLite, and fails startup rather than falling through to an empty database. Publication uses a directory-durable incomplete marker; an unconfirmed post-rename target is removed or rejected by the entrypoint instead of being accepted on restart. Settings patches reject unknown keys before transaction commit, and `backup.daily_hour` accepts only canonical integer strings from `0` through `23`, so a mixed invalid patch cannot partially persist.

## Web Console

The existing setup/login/settings/AdminModal/CN sync/AI/backup/entry save/save-next/shortcuts surfaces remain mounted. Current imports derive event segment identity from event/scenario/episode plus invariant original scenario position and field (`body` or `speaker`), never from filtered JP/CN output order; migrated filtered IDs remain explicitly opaque until reconciled by a current import, and Japanese rows remain addressable when Chinese is missing or source-equal. The console adds a locale selector and filter-independent shared dirty guard for locale, field/category/mode, row, arrow, Escape, logout, AI/retry/reorder reloads, collaborator event reloads from both event SSE names, and browser-unload transitions; localized updates use locale-specific SSE event names that old Chinese clients ignore. Any SSE disconnect locks content writes, and every reconnect performs an authoritative reload before unlocking. A `content.restored` event bypasses the ordinary save-first guard: stale buffers are captured only for explicit export/manual merge while the restored server version is loaded, so the revision-free compatibility entry route is not called by that conflict flow. The responsive lyrics workspace adds catalog search with stale-response suppression, source preview, performer selection, multilingual preview, optimistic conflict recovery, guarded song/publication transitions, draft save, and admin publication controls.

The console and direct `/workspace` client share the atomic local-storage envelope `moesekai-session-v1`, version 1 `{epoch, session}`, plus Web Locks `moesekai-workspace-identity` and `moesekai-workspace-refresh`. Login and refresh publish only after identity/token-version CAS; logout and terminal token-bound 401s publish a fresh-epoch null-session tombstone, while `/auth/me` network and 5xx failures preserve the envelope and expose an offline retry state; storage events propagate refresh, account switch, and logout to SSE/UI consumers. Both web clients open `/sse` with fetch streaming and the current envelope JWT only in `Authorization: Bearer`; query-token authentication is rejected, no normal JWT enters an SSE URL or log path, and every bounded-backoff reconnect rechecks the accepted epoch and current token. A valid envelope is never replaced by split-key migration, legacy keys migrate once under the identity lock, and malformed envelopes or roles outside `editor`/`admin` are unauthenticated. This prevents stale tabs from restoring an old identity or token while allowing the console and workspace to coexist on one origin.

Official-CN and JP-pending sync validate and canonicalize every JP episode scenario before calling the event replacement transaction; one failed fetch or validation skips the complete event. A pre-pass safely fills missing or stale scenario side rows for already official/human-preserved events without changing titles, translations, sources, revisions, or public files.

A separately built SekaiText-Moe web workspace is mounted from `WORKSPACE_WEB_DIR` at `/workspace/`. Its schema-version-3 manifest fixes producer repository/revision/dirtiness/production identity, app/base-path/entrypoint identity, source/editor-gate contracts, each sorted direct-client route's authentication mode (including bearer-only `GET /sse`), producer-proof requirement, and exact allowed roles, plus a sorted closed-world size/SHA-256 inventory. NEXT independently rejects unknown or duplicate JSON fields, unsupported contracts, unsafe paths, route/inventory ordering or duplicates, symlinks/nonregular/missing/extra/tampered files, resource-limit violations, nonproduction or dirty production producers, and a manifest-byte digest different from `WORKSPACE_MANIFEST_SHA256`. It has its own SPA fallback and immutable `/workspace/assets/` caching and never falls through to the existing `WEB_DIR` admin console. `moesekai-server --verify-workspace` applies the same env/config verifier without database or background startup. The Dockerfile's default `paired` stage makes all of `/app`, including binaries, console files, and the BuildKit `workspace` named context, root-owned and non-writable to runtime UID/GID `65532:65532`; only `/data` and explicit temporary locations are writable. CI runs it with a read-only root, a persistent `/data` volume, and a bounded `/tmp` tmpfs; proves lock contention fails, persistent restart succeeds without bootstrap admin input, and `docker stop` produces a bounded clean exit. Pairing verifies during the image build, while backend-only builds explicitly target `runtime`. CI also emits one deterministic `moesekai-rollback.tar` containing mode-preserving binaries, exported web files, and `SHA256SUMS`.

The production pairing workflow is manual-only, restricted to the protected NEXT default-branch revision and `production` environment, and accepts only an official `v<strict SemVer>` Moe tag plus a 40-character lowercase Moe commit. A single-repository, contents-read GitHub App token recursively peels the official Git tag to that commit and selects only the five commit-addressed workspace release assets from an official `immutable: true` private `SnowGlow-aww/SekaiText-Moe` release; installers remain undisclosed and unconsumed. NEXT bounds each remote asset before download, requires every downloaded byte count to equal release metadata, and validates exact local and remote asset identity, all sidecars, archive and manifest digests, the mandatory Sigstore bundle's GitHub Actions issuer, exact official `release.yml@refs/tags/<tag>` certificate identity, exact Moe workflow SHA, and canonical clean production manifest identity. Before extraction it rejects absolute/traversal/backslash/duplicate/case-collision paths, links/devices/nonregular entries, wrong top-level paths, trailing members/data, bounds violations, and archive/manifest extras, then extracts into a fresh directory and runs `workspaceverify.Verify` in production mode.

The resulting default `paired` target uses approved digest-pinned bases and initially pushes only a run-scoped staging tag. The digest is keylessly signed and custom-attested with the exact NEXT workflow SHA; NEXT then decodes and validates the full attestation predicate and image subject. Only after verification does it promote the digest to pair-specific tags containing the NEXT full SHA and Moe tag or full commit. Existing same-digest final tags are idempotent, different digests and `latest` are rejected, and both final tags are rechecked. OCI labels and the custom paired predicate bind NEXT revision, Moe tag/revision, archive digest, manifest digest, and final image digest. Standard GitHub provenance and a matching GitHub custom attestation are additionally required only when the explicitly configured private-repository capability variable is enabled. Repository-wide concurrency, registry tag immutability, and restriction of package-writer access to this workflow are mandatory to close publication races. Publication is environment-gated and produces a final digest but performs no deployment.
